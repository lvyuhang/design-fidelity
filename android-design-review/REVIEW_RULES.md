# 视觉走查规则 v11：单份设计稿模式

目标：在只有当前蓝湖设计稿、当前截图和已采集设备信息的条件下，找出有证据的还原问题。先判断可比性，再判断差异；不以问题数量、覆盖项数量或零问题为目标。不要求补充状态设计稿，不假装拥有组件规范、源码或业务规则。

## 1. 先确认环境与页面

- 区分物理分辨率、显示密度、屏幕逻辑尺寸、应用可用内容区、字体缩放、系统栏、安全区、键盘和滚动位置。只使用截图时的已知信息，缺失项标未知。
- 蓝湖画布单位不自动等于 dp；整屏尺寸不自动等于应用内容尺寸。不能将两张整图拉伸到同高同宽后，用表观大小判定缺陷。
- 同一业务页的数据或状态不同，仍检查其中共同组件；明确不同页面才判不匹配。局部选区只需确认其中组件可对应。

## 2. 拆分并建立组件对应关系

先记录本次实际可见的组件及两侧对应依据，而不是直接罗列差异：

| 组件族 | 必查项目 |
| --- | --- |
| 页面骨架 layout | 内容边界、页边距、列数、列宽关系、列/行间距、栅格对齐、固定区与滚动区关系 |
| 顶部 header | 标题字形/字号/字重/基线；返回和各操作控件的轮廓/填色/尺寸/留白；顶部下沿分割线、局部暗带、阴影及过渡 |
| 内容 content | 按语义角色、变体和状态归类重复卡片；容器比例/圆角、图片槽、文字、徽标、按钮、基线与内部间距 |
| 底部 navigation | 容器宽高/位置、图文、选中背景、文字到选中背景四边留白、图文间距；描边、阴影、透底及模糊 |
| 覆盖层 overlays | 当前可见弹窗、浮动按钮、遮罩、键盘避让；容器、内容区、操作区和留白。浮层可能出现在任意分区 |

- 按角色匹配，不按两侧第几个、同一行或照片相似程度匹配。不同卡片变体不强配尺寸。
- 每种可见且可比的重复卡片，优先检查两个完整实例（不足两个时如实说明），先检查共同模板，再检查状态相关子控件；不逐张重复报告同一根因。
- correspondence 的 match 只能是 same_variant（同变体可比）、state_uncertain（对应控件状态待证）、different_variant（不同变体）、not_comparable（无对应/证据不足）。标明仍可检查的共享属性和不可判断项。

## 3. 将适配问题与还原问题分开

- 区分固定逻辑尺寸、随空间伸缩、条件触发布局变化；没有规范时只根据可见证据提出假设，不自行规定 16dp 页边距、固定字号、断点或固定列数。
- 不同可用宽度下，卡片正常伸缩、长文字合理换行/截断、系统安全区或键盘引起的位置改变，不直接判缺陷。
- 跨宽度优先检查约束：左右对齐、边距关系、列间距一致性、图文是否挤压、非预期重叠/截断、固定区域是否正确避让。不要要求整页等比例缩放。
- 字数/位数变化不凭总宽断定字号；图片裁切不同不凭人物大小断定卡片高度。环境不同不能统一豁免控件自身的轮廓、填色及相对留白问题。
- 单份稿无法证明适配规则时，限制结论范围；不能据此声称适配通过，也不把所有可能的适配解释都转成人工核对点。

## 4. 单份稿下处理数据、变体与状态

- 照片、头像、昵称、余额、价格、计数等数据值不同不报缺陷，其所在组件的可比样式仍需检查。
- 在线/忙碌/离线等有可见依据的状态变化，只排除相关状态文案、颜色或可用性；共同容器、文字基线及普通操作组件继续比较。
- 将卡片拆成公共骨架与条件内容。有无个性标签、计价/魅力值、赠送权益、首充/普通充值等信息差异，不能仅凭当前一份稿断言业务缺失或样式错误。无对应变体时注明局限，继续查公共部分。
- 只有颜色变化本身，不能循环证明控件状态一定不同。筛选/开关/勾选等共同功能控件外观明确不同、没有额外激活状态证据时，保留蓝色待核对点，写清一次具体核对动作；同状态仍不同才判橙色样式问题。
- state_differences 只记有图像或上下文证据的状态/数据变化；“可能是配置不同”不能当作已知事实。不为每个业务猜测创建蓝点，不要求用户先补设计稿才能继续分析。
- 一侧首行截断、另一侧完整露出时，首卡顶间距/圆角不能直接硬比。固定顶部的分割线和阴影仍要独立检查；滚动内容被固定底栏覆盖不自动等于遮挡缺陷。

## 5. 视觉效果独立走查

- 分割线/描边、组件背景、边界阴影、毛玻璃透底是不同属性，分别核对。不要用“背景偏灰”替代“标题栏下沿暗带偏重”，也不要用“底栏透底”替代选中项内部留白检查。
- 先定位两侧真实组件边缘，再看邻近窄带的明暗、过渡宽度、阴影强弱和扩散；裁切边缘不是组件边缘，固定比例特写仅用于提醒注意，不代表已定位组件。
- 背景照片不同会改变毛玻璃后的颜色与对比。只能在可对应背景或有独立边缘证据时判断效果偏差；其他情况注明无法分离背景影响。
- 用“可见暗带更深/扩散更宽/遮挡更弱”等描述证据，不从截图虚构阴影半径、透明度、模糊参数或源码原因。方向不确定时不强行写偏重或偏弱。

## 6. 输出与复核

- 先输出 comparison_basis：环境判断，以及本区实际组件的 match、状态依据、适配依据、检查属性和局限。它是待复核的观察，不是已证实业务规范。
- 每个候选必须有 component、reference、actual、comparability、alternative 的具体证据；不能只写“大小不对”。状态不明与证据不足要区分。
- 橙点：共同可比属性存在明确样式偏差，复核 confidence >= .85。蓝点：共同功能控件的外观差异明确，状态尚未证实且有具体核对动作，复核 confidence >= .8。模型置信度不代表已校准的准确率。
- 数据/已知合法状态/可解释环境差异不打点；无法对应或缺乏证据的项目不强判。未检出不等于全页通过，summary 与 coverage 必须如实标明局限。
- 同组件同根因合并；不同属性只有独立证据才分别报告。重新分析已清除上轮AI标注，不根据上轮AI结论抑制本轮发现；existing_issues仅含保留的手动标注，已有同因手动问题不重复创建，手动标注不改写。候选复核通过后才生成可编辑标注。
- 点位放在截图中实际差异的位置；同类问题用代表实例打点。描述优先写原稿预期、截图实际及可比依据，不猜实现方案，不扩大成业务结论。
