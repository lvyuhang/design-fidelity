# 高效执行：减少重复工作，按复杂度计时

优化的对象是重复取证、缺字返工、临时脚本和无效重试。页面实现、源矢量与效果审核、交互验证和最终视觉检查所需时间允许随复杂度变化。没有通用分钟数、token 上限或调用次数达标即通过的规则。

## 一次准备，逐页复用

项目已有 Python 环境、Flutter 渲染测试、字体与预览外壳时直接复用。仅为新页面增加实现、测试参数与源节点映射。使用本 Skill 的通用预检和运行器，不为每页复制一套计时/日志程序。环境首次安装和通用工具维护时间单独记录，同时保留用户总等待时间。

编码前优先执行 [prepare_page.py](preparation.md)；按摘要处理输入问题，不等契约写完才发现缺字。审核规则以 JSON spec 声明，交给 `compile_contract.py` 生成 coverage/哈希；不再临时编写逐页契约构建 Python。Flutter 复制一次统一 harness 后只传页面参数。此优化减少的是模型往返和返工，验证脚本自身已经很快时不再微优化其耗时。

overview 负责盘点和定位；原始字号、字重、颜色、行高、矢量、裁剪与父级效果来自 inspect。相同 snapshot 下独立区域读取可批量或有界并发；页面版本、身份不同的证据不可合并。节点数齐全不能替代样式审核。

取证后、编码前先检查文字样式：

```sh
python "$SKILL_DIR/scripts/preflight.py" \
  --evidence .design-fidelity/page/overview.json \
  --evidence .design-fidelity/page/region.json \
  --output .design-fidelity/page/evidence-check.json
```

退出 2 时从报告的 `style_gaps` 提取节点 ID，定向补取。该工具仅验证文字样式字段是否存在，不证明分页完整、矢量可绘制、所有混合文本 run 的样式正确，也不自动决定缺图或忽略节点。已烘焙文字仍按节点实现决策处理；不要填入猜测样式来消除预检问题。

编码前把新增页文本并入字体字符清单，检查实际所用字重的 cmap。扩充子集保留已交付页面字符，记录原字体来源；不因缺字偷偷替换字体。资源按哈希复用，核对源画框与透明边距后才复用布局。

## 降低往返和返回量

完整 JSON、资源 manifest、二进制内容保存到项目证据目录。可用执行工具编排 MCP 时，让数据直接经文件工具落盘；只向模型回传身份、画布、节点/资产数量、必要样式摘要、缺口与路径。不要回显 base64 或将数万字门禁报告完整打印。

资源优先使用客户端可用的文件/资源交付能力，保存后检查长度与哈希。不能把服务端缓存路径当成本地文件。一次失败后查明错误类型：鉴权失败、内容截断、分页参数、落盘失败分别处理，不重复尝试同一失败路径。复用本地资产只减少本地传输，不代表服务端没有下载；统计时区分。

样式、资产、环境确认后集中实现，再集中修改同一轮真实差异。已有完整门禁足够快时直接使用，不另造局部调度器。修正读取失败 ROI 和必要局部证据；无版本变化不重新拉整个项目。

## 单命令验证

独立预检：`python "$SKILL_DIR/scripts/preflight.py" --contract CONTRACT --output REPORT`。
新页加 `--require-style-evidence`，旧页回归不加时仍把样式缺口写入报告；`READY_FOR_RENDER` 只表示输入预检，不是视觉验收。

Flutter 示例：

```sh
python "$SKILL_DIR/scripts/run_flutter.py" \
  --contract .design-fidelity/page/visual-contract.json \
  --app flutter_app --test test/page_render_test.dart \
  --output-env PAGE_RENDER_OUTPUT \
  --output .design-fidelity/page/r0 \
  --require-style-evidence \
  --analyze lib/page.dart test/page_render_test.dart
```

渲染测试必须读取 `PAGE_RENDER_OUTPUT` 环境变量写入 PNG，并使用契约的画布、倍数、字体、阴影与页面状态。输出目录必须全新，命令路径按 `--app` 解析。运行器不修改契约、自动放宽门槛或重刷哈希。回传简短状态、失败检查和日志路径；完整输出保存在各阶段 `.log` 与 `run.json`。

最终交付加 `--build`，迭代期间无需反复发布构建。`--analyze` 使用 Dart analyzer；项目有其他必需检查仍须执行。已知环境失败只在对应环境下采用验证过的替代路径，不跳过静态分析。最终还须查看真实并列图和可运行预览。

## 如何判断优化有效

记录从用户请求到最终预览/回复的总时间，以及取证、实现、修正、验证、构建、工具维护阶段。失败、重试、等待全部纳入；自动运行器耗时只是其中一部分。

比较相近复杂度、相同模型/推理强度、渲染环境、素材缺口和验收规则。复用旧页与独立新布局分开标注。不据一次缓存回放宣称首次页面实现提速或品质完全不变。

优先观察重复调用、失败重试、缺证据/缺字返工及人工调参轮数是否下降，再看时间和 token。token 分列输入、缓存输入、输出；推理 token 若已计入输出，不重复累加。“非缓存输入 + 输出”可以记录，但不是全部成本或计费量。无法取得使用日志时明确标记不可用。

质量标准沿用已冻结契约和人工视觉复查；发现漏检保留旧契约、另建修订并通过故障样本证明。每次试验应针对具体重复成本，不为追求速度删检查，也不因单次失败无限增加流程。
