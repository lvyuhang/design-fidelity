# 验证方法与边界

仅维护 Skill 或评估迁移能力时读取。项目名、源节点 ID、截图、时长和历史修复记录留在业务项目；日常开发不加载这些材料。

## 检测器维护

- 随包 tests 使用合成数据验证通用行为。新增/修改检测逻辑，或 SDK、字体、渲染器变化影响结果时，运行相关回归；发布检查工具前运行完整套件。
- 每类新检测至少包含正确样本与对应错误样本；前者应通过，后者应失败。检查遗漏、尺寸/位置、透明度/描边等机制，不为某个业务名称写特例。沿用已验证的检测器不必每页重新注入错误。
- 每张新页面仍需原稿检测器自检、源覆盖检查和本次真实渲染验收。算法已通过测试不等于当前 ROI、颜色分割或遮挡判断必然有效。

```sh
python -m unittest discover -s /path/to/lanhu-design-fidelity/tests -v
```

首次 Flutter 环境接入可复制 assets/flutter-smoke 到独立临时目录，安装依赖并填写实际 renderer/engine 信息，按 usage.md 的收据流程分别运行 OFFSET=0 与 OFFSET=4。预期正确样本通过、位移样本失败；合成夹具不能充当真实页面还原成绩。

## 跨项目验证

1. 冻结 Skill 文件哈希、模型/推理强度、框架环境与缺图策略。单独保留项目接入成本；取证、编码、修正、验收、构建和可访问预览计入总等待。token 只用实际计量，缺失记 null。
2. 先选未参与调优的陌生项目一页，包含该项目常见的布局、文字、资产和效果。实现者使用独立上下文，仅获得固定 Skill、当前项目说明和设计入口，不继承旧页面代码或修复提示。
3. 首次渲染前固定当前页验收标准，保存首版。原稿与真实 Flutter 渲染按源逻辑尺寸对照；记录首次遗漏、门禁漏检、人工介入及最终残余差异。门禁结果之外，由未参与实现的复核者核对完整页与关键细节，避免实现和检查同时遗漏。
4. 再选择其他业务项目及不同布局/效果类型，至少覆盖三个项目。先完成同一冻结版本的测试批次，再归纳缺陷；若中途修改 Skill，新结果另列版本，不与旧成绩混算。三项目只是初步迁移证据，不保证任意项目通用。
5. 成功标准包含：无需给 Skill 加项目特例、无未处置的可见节点、独立复核无阻断性残余差异；缺图按既定策略披露。2–3 轮是效率目标，超出如实记录。比较质量合格页面的总耗时/token，失败和未完成样本不得删除；简单页通过不能抵消复杂页失败。

## 失败归属

- 证据缺字段或解析差异：修 MCP/框架适配层。
- 源信息存在但简报/实现遗漏，或检查放过错误：修通用规则/工具，并加最小合成反例。
- 项目字体、画布、资源或业务约定不同：写入项目配置，不扩充 Skill 默认指令。

修订后先回归受影响样本，再用未参与修订的页面验证。禁止仅凭同一页面反复调优后的通过率宣称跨项目提升。

当前能力边界是蓝湖证据与主要面向 Flutter 的渲染流程。节点符号映射不是运行时绘制证明；颜色分割需要语义核对；截图不验证业务逻辑或可访问性。跨项目结果由各次实验单独证明，不从合成测试数量推导。

根因验证先复现冻结基线，再只改变一个处理环节，比较对应局部与整页像素。存在重复代码或缺字段并不证明它造成当前可见误差；无像素变化应撤回该视觉归因。合成反例验证检查器能力，不计作模型生成页或整页视觉验收。
